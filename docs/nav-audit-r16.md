# R16-c — تدقيق بنية التنقل والتكرار (مواصفة إعادة هيكلة — مراجعة فقط)

**التاريخ**: جولة R16 (ما قبل تثبيت v1) • **الأساس**: قراءة فعلية للكود بأرقام أسطر (b0de433 / v0.11.0، 752 اختباراً أخضر) • **شكوى المالك**: «تكرار عالٍ في مصادر الوصول لشيء معين، ولا يوجد تنظيم جيد — الوصول لمكان واحد من عدة أماكن، وتكرار لأجزاء تؤدي نفس الوظيفة».

**القاعدة الحاكمة المقترحة**: لكل شاشة **مسار أساسي واحد واضح** (المحور الطبيعي لها) + **اختصار واحد كحد أقصى** من الداشبورد للأفعال اليومية + استثناءان مشروعان: أزرار سياقية عميقة داخل المستندات (مرتجع من تفاصيل فاتورة) وحالات Empty/خطأ التي تقترح الفعل الطبيعي. ما عدا ذلك = زائد.

### 1.3 ملاحظات بنية عالية الأثر

1. **محور الأطراف يتيم**: الداشبورد يخطف أبناءه الثلاثة (عملاء/موردين/أسعار) بروابط مباشرة (home:223/232/255) فلا يبقى أي سبب لزيارة `/parties` — بينما أرصدة العملاء/الموردين (إدارة تحصيل يومية) محبوسة خلف محور لا يدخله أحد إلا بالخطأ (رجوع من aging). **هذا عيب «التنظيم» الحرفي بشكوى المالك**.
2. **التكرار داخل المحاور الواحدة**: قالب «محور = بطولة + بلاطتا إحصاء + بطاقة فعل + بطاقتا وصول + أزرار AppBar + عرض الكل» يولّد 5 مداخل لقائمة الفواتير داخل شاشة واحدة (البيع 77/198/211/335/459 والشراء 82/201/212/329/452).
3. **المشتريات بمركزين**: مدخلان من خارجها (home + sell hub) تطلبا بنية PurchasesOriginTracker (app_router:71-88) ليعود زر الرجوع للأصل — علاجٌ لمشكلة تعدد المداخل بدل تقليصها.
4. **مركز التقارير خلف «المزيد»** (settings:131): أداة الرقابة اليومية مدفونة في تبويب الإعدادات؛ مع أن الشريط الخمسي ثابت (قيد ملزم) يبقى موضع نقاش: بلاطة تقارير بالداشبورد أرخص من تغيير الشريط.
5. **Dead code**: `coming_soon_screen.dart` (placeholders/) غير موصول بأي مسار ولا مستورد بأي ملف — 60 سطراً ميتة تزيد مساحة الاختبار الوهمية.

### 2.2 تكرار الشاشات (أزواج بديلة)

- **لا توجد قائمتان لنفس البيانات** بحمد الله: قائمتا العملاء/الموردين تُبنيان من ملف واحد بمعامل kind (parties_list_screen.dart:29/62) وأرصدة القبض/الصرف كذلك (party_balances_screen.dart:29/57) — **هذا هو النمط المرجعي الصحيح**.
- فواتير البيع مقابل فواتير الشراء: بنيتان متوازيتان (~600 سطر لكلٍّ) بنفس الهيكل (بحث+فلاتر+قائمة+تفاصيل) لكن بيانات مختلفة — مقبول محاسبياً، والرابح توحيد المكونات المشتركة (بحث/فلاتر/بطاقة مستند) لا دمج الشاشات.
- كشف الحساب (party_detail) مقابل أرصدة الأطراف (party_balances): وظيفتان مختلفتان (حركة موثقة مقابل رصيد مجمّع) — لا دمج.
- أعمار الديون مقابل أرصدة العملاء: متكاملان (تصنيف FIFO مقابل إجمالي) — لا دمج، لكن مدخلا aging المتعددان بلا اتساق رجوع (§1.3-3).

### 3.3 تأثير UX — الترتيب الهرمي المقترح

- **الشريط الخمسي ثابت** (قيد ملزم). ترتيب الحياة اليومية: الرئيسية (نظرة) → المخزون → **البيع وسطاً** → النقدية → المزيد.
- **تبويب «المزيد» الحالي مرتب أصلاً ترتيباً سليماً** (بطاقة المنشأة → التقارير → التخصيص → الأمان → البيانات → حول): يُثبَّت كما هو لـv1؛ التعديل الوحيد المقترح داخله: لا شيء (تغييره يزيد مساحة الاختبار بلا مكسب).
- **المحاور بعد التقليم (النموذج المعياري)**: بطاقة بطلة = هوية الوحدة • بلاطات إحصاء **معلوماتية** (بلا تنقل مكرر) • **بطاقة فعل واحد** (فاتورة جديدة) • بطاقات وصول للأقسام (واحد لكل قسم) • قائمة «آخر…» بـ«عرض الكل» وحده. النتيجة: قائمة الفواتير بمدخل واحد داخل محورها + Empty.
- **الداشبورد بعد الدمج**: 4 بلاطات اليوم + مبيعات الشهر + رسم 30 يوماً + تنبيهات + وصول سريع: **المخزون/الأطراف/المشتريات** (+ خيار منسق: التقارير أو الوردية بالخانة الرابعة) — كل بلاطة تشير لجذر وحدة واحدة لا لعمقها.
- **قاعدة الدليل البصري للرجوع**: كل شاشة عمق ترجع لجذر وحدتها حصراً (تصحيح aging يغلق الحالة الوحيدة المخالفة بعد A6).

### 3.4 مخاطر التنفيذ (ملزمة للمنفذ)

1. **RefreshOnActive/RefreshOnReturn لا تُمس**: 18 غلافاً RefreshOnActive بمسارات RegExp (جدول §قياس أعلاه) و6 RefreshOnReturn — كلها مربوطة بالمسار لا بزر الدخول، فحذف الأزرار الزائدة آمن عليها، لكن أي «تحسين» يستبدل مساراً بآخر يكسر النمط.
2. **تجميد بنية URL**: لا إعادة تسمية ولا نقل مسارات (v1 قريباً؛ deep-links مثل `/purchases/returns/sale?invoice=` و`/cash/movements?box=` و`/parties/customers/form?edit=` موصوفة بسجلات واختبارات).
3. **الاختبارات**: 752 خضراء تشمل مفاتيح واجهة (مثل `shell_sell_button` و`home_purchases_tile` و`pur_new_purchase_card` بـsell_fixes_test). كل بند حذف يتطلب تحديث الاختبارات المرتبطة بالمفتاح المحذوف فقط (مثل أيقونة AppBar — لا اختباراً معروفاً يعتمدها) وتشغيل حزمة القوائم المعنية.
4. **PurchasesOriginTracker يبقى** حتى بعد تقليص المداخل (احتياط المدخلين المتبقيين home/sell) — إزالته وفرٌ صغير بمخاطرة رجوع أعلى.
5. **A5 (دمج بلاطات الأطراف) هو الوحيد ذو أثر UX مُدرك**: يضيف نقرة للوصول لقائمة العملاء من الداشبورد. البديل الأرحم إن رفضه المالك: إبقاء بلاطة «العملاء» اليومية وبلاطة «الأطراف» للمحور (2 بلاطات بدل 3) — يظل المحور قابلاً للوصول. **القرار للمنسق/المالك**.
6. **W7-W11 بعد v1 حصراً**: توحيد المنتقات والأوراق المالية يغيّر متغيرات كثيرة دفعة واحدة — عكس هدف «تقليل مساحة الاختبار قبل التثبيت».
